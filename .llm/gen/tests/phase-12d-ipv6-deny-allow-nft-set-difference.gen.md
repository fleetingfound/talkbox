# Phase 12d: IPv6 deny/allow via nft set difference

Test document for [Phase 12d: IPv6 deny/allow via nft set difference (accept allow-set, then drop deny-set)](.llm/gen/plans/phase-12d-ipv6-deny-allow-nft-set-difference.gen.md), which eliminates the Bash-side CIDR carving entirely and moves the deny-minus-allow set difference into the nftables ruleset (an `accept` rule matching the allow set placed before a `drop` rule matching the raw deny set, per address family), resolving the `SPEC.md` §"network" violation that a broad IPv6 deny CIDR (e.g. `--deny-ip ::/0`) blocked the always-allowed `::1` loopback.

## New tests

### `test/unit/network.bats` (21 tests)

All 21 fail against the current implementation (the old single-set carve-and-emit code rejects the new two-array nameref calls with "invalid variable name for name reference", emits the old single-set ruleset, or invokes podman where the new contract requires a no-op). The rewritten `deny_allow_args` tests pin the new two-array output contract ("Rework `deny_allow_args` to produce **two** output arrays instead of one: the deduplicated raw deny set and the deduplicated allow set (the latter including the always-allowed entries `127.0.0.0/8`, `169.254.1.1/32`, `::1`). No carving is performed."): deny entries are returned raw, deduplicated, in order (file entries then CLI); allow entries are returned raw, deduplicated, in order (file, CLI, then the always-allowed entries); carving-specific assertions from Phase 12b are replaced by no-carving assertions, e.g. `--deny-ip ::/0` leaves `::/0` in the deny set while `::1` stays in the allow set, and a deny `10.0.0.0/8` stays whole despite an allow `10.0.0.0/9`.

The rewritten `nft_deny_ruleset` tests pin the two-set accept-then-drop ruleset ("for each address family that has deny entries, the emitted ruleset defines two interval sets — an allow set and a deny set — and two rules in the output chain: an `accept` rule matching the allow set (placed first) followed by a `drop` rule matching the deny set. Families with deny entries but no allow entries emit only the deny set and drop rule. Families with no deny entries emit nothing"): a mixed IPv4/IPv6 deny set with allows emits both families with `allowed` and `blocked` sets and `@allowed accept` before `@blocked drop`; a deny-only family emits no `allowed` set and no accept rule; a family present only in the allow set emits nothing; and the issue-resolution case (deny `::/0`, allow `::1` and `2001:db8::1`) emits the `ip6` allow set before the deny set — capturing "the resolution of the reported issue at the ruleset level" required by the plan. The exact asserted ruleset text was validated against `nft` (via `podman unshare bash -c 'unshare -n nft -c -f'`).

The rewritten `plan_nft_deny` / `install_nft_deny` tests pin the no-op rule ("`install_nft_deny` remains a no-op (and emits no `podman` invocation) when the deny set is empty; the allow set alone never triggers rule installation"): `plan_nft_deny` emits no tokens and the podman shim records no invocation for an empty deny set even with a non-empty allow set.

### `test/e2e/deny-allow.bats` (1 new test)

`onbox --deny-ip ::/0 keeps the IPv6 loopback ::1 reachable` — per the plan: "Add an e2e test (gated on `nft` availability and IPv6 host connectivity, skipping gracefully otherwise) that denies a broad IPv6 CIDR (e.g. `::/0`) and asserts that `::1` remains reachable inside the container (e.g. via a loopback IPv6 `curl`), demonstrating the spec compliance end-to-end." It skips via a new `require_nft_ipv6` helper when `nft`, `python3` or host IPv6 loopback (`::1` bind) is unavailable, serves a marker from the host `host_http_server.py` bound to `::1`, and asserts the container's `curl "http://[::1]:<port>/marker"` succeeds. Observed red against the current code: the container is blocked from `[::1]` by the `::/0` deny (the phase-12c ruleset drops egress to the blocked set, and `::1` is not carved out). The guest→host `::1` path was verified empirically with the current build before adding the test.

## Tests edited

- `test/unit/network.bats` — every `deny_allow_args`, `nft_deny_ruleset`, `plan_nft_deny` and `install_nft_deny` test rewritten to the new two-array interfaces, per the plan's test section ("Rewrite the `deny_allow_args` carving tests to assert the new two-array output… Rewrite the `nft_deny_ruleset` tests to assert the new two-set accept-then-drop ruleset per family… Update the `install_nft_deny` shim tests to thread both deny and allow sets and assert the no-op behaviour for an empty deny set"). The old assertions were inconsistent with the plan because the plan removes carving ("Remove the IPv4 carving helpers (`ipv4_int`, `ipv4_str`, `ipv4_prefix`, `ipv4_range`, `range_cidrs`) and `deny_allow_subtract` entirely") and replaces the single-set ruleset ("the emitted ruleset defines two interval sets"). The `port_args` tests are unchanged (that interface is untouched by the plan).
- `test/e2e/deny-allow.bats` — the shim test "onbox runs the nft installer for a non-empty deny set; offbox and an allow-emptied set do not" is edited: its allow-emptied-set sub-case asserted zero `nsenter.*nft` invocations for `onbox --deny-ip 1.1.1.1 --allow-ip 1.1.1.1`, which is inconsistent with the raw-deny-set design ("the deduplicated raw deny set"; "`install_nft_deny` remains a no-op … when the deny set is empty" — with a raw deny set, `--deny-ip 1.1.1.1 --allow-ip 1.1.1.1` has a non-empty deny set). The sub-case is inverted to assert the installer *does* run (≥1 invocation) when deny entries are present alongside allow entries, which is red now (the current carving empties the effective set) and green after implementation. The onbox-deny and offbox sub-cases are unchanged and still pass.
- `test/e2e/helpers.bash` and `test/e2e/host_http_server.py` — `start_host_http_server` accepts an optional bind address (default `127.0.0.1`) and the server script binds it (using `AF_INET6` when it contains `:`), enabling the new test's IPv6-loopback server. The existing IPv4 call sites (deny-allow, lifecycle) are unaffected and still pass unchanged.
- `test/e2e/deny-allow.bats` — the new `require_nft_ipv6` gate helper is added alongside the existing `require_nft_and_internet`.

## Tests removed

- `test/unit/network.bats` — "plan_nft_deny builds the podman unshare nsenter nft invocation tokens": the plan only changes `plan_nft_deny` by making it "carry both sets; no-op when the deny set is empty". Under the new nameref interface the positive token-building case (`plan_nft_deny out <pid> deny allow` with a non-empty deny array) is observationally identical before and after implementation, so the rewritten test passed against the current code and could not satisfy the red/green invariant ("All new tests fail when the commands `make test-unit` and `make test-e2e` are run"). The token emission for a non-empty deny set remains covered by the retained e2e shim assertion (`grep -c 'nsenter.*nft'` ≥ 1) and the retained no-tokens-for-empty-deny unit test.
- `test/unit/network.bats` — "install_nft_deny warns and returns success when the rules cannot be applied": the warn-and-continue behaviour is unchanged Phase 12c behaviour, not new behaviour of this plan; the plan's only new `install_nft_deny` requirement is the empty-deny no-op ("remains a no-op (and emits no `podman` invocation) when the deny set is empty; the allow set alone never triggers rule installation"), which the retained shim test asserts. The rewritten warn test passed against the current code and was removed for the same red/green reason as above.

## Implementation notes

- The tests pin the new internal interfaces so the implementation matches: `deny_allow_args <deny-out> <allow-out> <deny-file> <allow-file> <deny-cli> <allow-cli>` (arrays by name, outputs first, mirroring the pre-existing `_out`-first convention), `nft_deny_ruleset <deny-array> <allow-array>`, `plan_nft_deny <out> <pid> <deny-array> <allow-array>`, and `install_nft_deny <ctr> <deny-array> <allow-array>` — consistent with the plan's "the `run_*` executor parameter lists gain an allow-set nameref" and the codebase's nameref array-passing convention (`mount_entries`, `port_args`, executors).
- The ruleset text is pinned exactly: sets named `allowed` (accept) and `blocked` (drop), `add rule <family> talkbox_deny output <ip|ip6> daddr @allowed accept` emitted before `… @blocked drop`, per family, with no emission for families lacking deny entries.
- The e2e IPv6 test relies on pasta forwarding guest `::1` to the host loopback (the same mechanism by which the pre-existing tests reach `127.0.0.1` host servers); both paths were verified empirically before writing the test.
