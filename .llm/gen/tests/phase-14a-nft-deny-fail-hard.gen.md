# Phase 14a: `install_nft_deny` fails hard when the deny set cannot be enforced

Test document for [Phase 14a: `install_nft_deny` fails hard when the deny set cannot be enforced](.llm/gen/plans/phase-14a-nft-deny-fail-hard.gen.md), which reverses the "warn and continue" semantics of `install_nft_deny` so that a non-empty deny set which cannot be enforced (PID lookup failure or `nft` pipeline failure) aborts container orchestration by default (`TALKBOX_STRICT_NFT=0` restores the prior lax behaviour), surfaces the underlying stderr, and prepends `/usr/sbin:/sbin` to `PATH` inside the installer so `nft` installed at its standard location is resolved when off the caller's `PATH`. It also closes the test gap tracked in [install-nft-deny-no-nonempty-test.gen.md](.llm/gen/issues/install-nft-deny-no-nonempty-test.gen.md).

## New tests

### `test/unit/network.bats` (5 tests, plus 2 shim helpers)

The fake-`podman` shim is parameterisable per the plan's test section ("The fake-`podman` shim must be parameterisable (exit code of `inspect`, exit code of the `unshare`/`nsenter`/`nft` sub-invocation)"): environment variables `SHIM_INSPECT_RC`/`SHIM_INSPECT_STDERR`/`SHIM_PID` configure the `inspect` call, `SHIM_NFT_RC`/`SHIM_NFT_STDERR` configure the `unshare` sub-invocation, and `SHIM_LOG` records the `PATH` seen by the `nft` pipeline subprocess. A `path_without_sbin` helper strips any `/usr/sbin`/`/sbin` entries from the ambient `PATH` so the success-path assertion is deterministic.

- `install_nft_deny with a non-empty deny set fails hard when podman inspect fails to return a PID` — asserts a `talkbox:` error is emitted on stderr, the underlying `podman inspect` stderr is surfaced, and the function returns non-zero (PID-lookup failure path, strict mode). **Observed red:** the current code emits `talkbox: warning: …` and returns 0.
- `install_nft_deny with a non-empty deny set fails hard when the nft pipeline exits non-zero` — asserts a `talkbox:` error on stderr, the underlying `nft`/`nsenter` stderr is surfaced (not suppressed), and the function returns non-zero (nft pipeline failure path, strict mode). **Observed red:** currently the pipeline stderr is swallowed by `>/dev/null 2>&1` and the function warns and returns 0.
- `install_nft_deny with a non-empty deny set applies the rules and resolves nft via the augmented sbin PATH` — asserts the success path returns 0 and emits no `talkbox:` warning/error, and that the `nft` pipeline subprocess sees a `PATH` beginning `/usr/sbin:/sbin:` (the plan's "Prepend `/usr/sbin:/sbin` to `PATH` … so `nft` and `nsenter` are resolvable when installed at their standard locations but off the non-root `PATH`"). **Observed red:** no augmentation exists today, so the recorded pipeline `PATH` does not start with the sbin prefix. The assertion is made on the `PATH` observed by the fake `podman` shim rather than by genuinely resolving a fake `nft` from a sbin directory: real resolution happens inside `podman unshare nsenter` (children of the `podman` process), which a unit test cannot enter, and the standard sbin directories are root-owned (`/usr/sbin` is not writable by the non-root test user), so a fake `nft` cannot be placed there. An `nft` inherited through the pipeline's augmented `PATH` is exactly what the recorded prefix guarantees, and genuine resolution is covered by the e2e suite on hosts with `nft` installed.
- `install_nft_deny with TALKBOX_STRICT_NFT=0 warns and returns 0 when podman inspect fails to return a PID` — asserts the prior warn-and-return-0 behaviour (lax PID-lookup path), per the plan's test section ("asserts the prior warn-and-return-0 behaviour (lax PID-lookup path)"). This pins preserved behaviour, so it passes before and after implementation (a guard, like the phase-11a guard documented in [phase-11a-entrypoint-readiness-sync.gen.md](.llm/gen/tests/phase-11a-entrypoint-readiness-sync.gen.md)); the lax path is observationally identical pre- and post-implementation because `TALKBOX_STRICT_NFT` is currently ignored and the default warn-and-continue coincides with lax mode.
- `install_nft_deny with TALKBOX_STRICT_NFT=0 warns and returns 0 when the nft pipeline exits non-zero` — asserts the prior warn-and-return-0 behaviour (lax nft-failure path). Same guard status as above; the plan notes stderr "may still be surfaced" in lax mode, so only the warning text and status are asserted.

The existing empty-deny-set test (`install_nft_deny with an empty deny set performs no podman invocation even when the allow set is not empty`) is unchanged and continues to pass (the plan: "The empty-deny-set path is unchanged (no `podman`/`nft` invocation, returns 0)").

### `test/e2e/deny-allow.bats` (no-warning assertions added to 4 passing-path tests)

Per the plan's test section ("Add an assertion to the existing passing-path `onbox`/`netbox` deny tests that the run emits **no** `talkbox: warning:` / `talkbox:` error line on stderr, so a silent-fallback regression is caught on hosts where `nft` is available"), the following existing tests each gained `[[ "$output" != *'talkbox:'* ]]` on their passing-path runs, remaining gated behind `require_nft_and_internet` / `require_nft_ipv6`:

- `onbox --deny-ip blocks a denied address while a non-denied address remains reachable`
- `netbox --deny-ip blocks a denied address while a non-denied address remains reachable`
- `onbox --deny-ip ::/0 keeps the IPv6 loopback ::1 reachable`
- `a deny entry overridden by --allow-ip remains reachable` (both runs: deny-only and deny-overridden-by-allow)

These are regression guards: on a healthy host (rules applied, no failure) they pass before and after implementation, and they fail if a future change silently falls back to warn-and-continue or emits a spurious `talkbox:` line. The plan explicitly leaves the `export PATH="/usr/sbin:/sbin:$PATH"` in this file's `setup()` in place ("it is harmless and keeps the tests robust if the implementation detail changes"). No `TALKBOX_STRICT_NFT=0` e2e test was added: per the plan, it is "only viable on hosts where `nft` can be made to fail deliberately … so this may be left as a unit-only assertion", and the unit tests above are the primary coverage for the lax path.
