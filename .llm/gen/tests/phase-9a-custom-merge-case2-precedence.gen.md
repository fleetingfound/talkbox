# Tests: Phase 9a `custom_merge` Case 2 precedence over Case 1

Linked plan: [phase-9a-custom-merge-case2-precedence.gen.md](../plans/phase-9a-custom-merge-case2-precedence.gen.md)

Summary: this phase adds red-green regression tests for the shared-worktree `custom_merge()` fix which reorders `custom_merge_current()` so Case 2 (`git reset --mixed`) is evaluated before Case 1 (`git merge --ff-only`) when the worktree already matches the remote ref but contains host-untracked files newly introduced by the remote commit, resolving [custom-merge-case1-shadowing-case2.gen.md](../issues/custom-merge-case1-shadowing-case2.gen.md); the merge/sync subcommand interface is unchanged.

## New tests

Unit test (`test/unit/merge.bats`):

- `custom_merge applies Case 2 when an untracked file introduced by the remote already matches the worktree` - builds the fixture-repository shared-worktree situation directly: a commit on a throwaway branch newly introduces the file `test`, which is pushed to `origin/<branch>`; on the checked-out branch the same file is then created in the working tree with identical content as an **untracked** file. It asserts `custom_merge origin <branch>` succeeds, advances `HEAD` (and the branch ref) to the remote ref, leaves `test` unmodified on disk, and emits no `talkbox:` warning. This pins the plan's Test bullet: "a commit that newly introduces a file (e.g. `test`) ... with identical content as an untracked file; assert that `custom_merge origin <branch>` succeeds, advances `HEAD` to the remote ref, leaves `test` unmodified on disk, and emits no `talkbox:` warning", together with [SPEC.md §`custom_merge()`](../../../SPEC.md) Case 2 ("If there are no staged changes and the worktree already matches `refs/remotes/<remote>/<branchname>`, update the current branch using `git reset --mixed`"). Against the current implementation the test fails because Case 1 runs `git merge --ff-only` first, which refuses with `error: The following untracked working tree files would be overwritten by merge`.

End-to-end test (`test/e2e/merge-sync.bats`), run under the existing `systemd-run`-wrapped runner:

- `onbox merge fast-forwards when the container commit introduces a file untracked in the host worktree` - mirrors the issue's reproduction: inside an `onbox` container a new file `new-file.txt` is created and committed (appearing in the bind-mounted host worktree, where `git status --porcelain` shows it as untracked `?? new-file.txt`), then on the host `onbox fetch` and `onbox merge` are run. It asserts the merge succeeds, `HEAD` advances to the container commit, and the file is present and unchanged on disk. This pins the plan's Test bullet: "inside an `onbox` container, create and commit a new file; on the host ... run `onbox fetch` then `onbox merge`; assert the merge succeeds, `HEAD` advances to the container commit, and the file is present and unchanged on disk". Against the current implementation the test fails with the same git overwrite-refusal error (`error: The following untracked working tree files would be overwritten by merge: new-file.txt`).

## Tests edited

- None of the pre-existing `custom_merge` tests needed editing. All pre-existing `custom_merge` unit and e2e tests remain consistent with the plan's reorder. The plan's Tests section states "Existing Case 1 / Case 2 / Case 3 tests must continue to pass unchanged", and its Design section explains why each still passes after the reorder: the clean-worktree fast-forward ("the worktree holds `base` while the remote holds `two`, so `worktree_matches_tree` returns false and Case 1 still fires"), the untracked-files-present fast-forward ("the untracked file is not part of the container commit, so the worktree tree differs from the remote tree and Case 1 still fires"), and the conflicting-untracked-file refusal ("the untracked `new.txt` differs in content from the committed version, so the worktree tree differs from the remote tree, Case 2 does not apply, and Case 1's refusal is preserved"). No assertions in these tests need changing.
- `test/runner.mk` and `test/run-suite.sh` — the `GLOBAL_TEST_TIMEOUT` default is raised from 600 to 900. Justification: the plan mandates a new container-based e2e regression test ("Run under the existing `systemd-run`-wrapped runner"), which adds ~9s to an e2e suite that already runs ~594s against the 600s default (99% of the budget). With the test added the suite takes ~603s, so `make test-e2e` with the default 600s limit reproducibly timed out at the suite level before the final tests could run, recording `exit: timeout` and risking the new test being observed as a timeout rather than a functional failure. The default is only a fallback ceiling (the runner's smoke tests assert only that it is a positive integer, not its value), and raising it to 900 keeps `make test-e2e` completing while still bounding runaway suites.

## Tests removed

- None. No pre-existing test is inconsistent with the plan: the reorder only changes which of Case 1 / Case 2 fires in the overlap where the worktree matches the remote ref while host-untracked files are present, and the existing tests exercise no such combination (the existing Case 2 test modifies a tracked `file.txt`; the existing untracked-file tests use files absent from, or conflicting with, the container commit), so all of them remain valid and green after implementation.
