# Tests: Submodule gitdirs in the container (gitdir-volume inclusion and targeted write prevention)

Linked plan: [submodule-gitdir-inclusion-in-container.gen.md](../plans/submodule-gitdir-inclusion-in-container.gen.md) — implements the second half of SPEC.md's submodule support ("absorbed into the host's top-level git directory **and then included in the container**") by copying `/host/git/modules` into the container gitdir volume in `image/setup.sh` with a per-module `core.worktree` rewrite and targeted read-only `objects/`/`refs/` permissions, and revises the submodule e2e test accordingly.

Related documents: [submodule-gitfile-dangling-in-container.gen.md](../issues/submodule-gitfile-dangling-in-container.gen.md), [submodule-modules-inclusion-mechanism.gen.md](../choices/submodule-modules-inclusion-mechanism.gen.md), [submodule-write-prevention-in-container.gen.md](../choices/submodule-write-prevention-in-container.gen.md).

These are red-phase tests: they were written and confirmed to fail against the current implementation, and are expected to pass once the plan is implemented. All live in [test/e2e/git-transport.bats](../../../test/e2e/git-transport.bats), plus one file-local fixture helper (`mk_submodule_source` in the same file) used by all four tests.

## New tests

- `submodule reads work in the container while submodule history writes are prevented` — fixtures a project with one absorbed submodule and an `onbox` container, then asserts `git -C sub status` succeeds and reports `working tree clean`, while `git -C sub update-ref refs/heads/sub-blocked HEAD` and `git -C sub commit --allow-empty` both fail (history writes into the copied module's `refs/` and `objects/`). This pins the plan's external-facing functionality: "Submodule-level *history-writing* git operations (`commit`, `add`, `update-ref`, `tag`, …) inside the container fail with permission errors, while submodule *reads* (`git -C <sub> status`, `log`) work — enforcement is by non-writable `objects/` and `refs/`", and [SPEC.md](../../../SPEC.md) "git operations within a submodule are prevented within the container and must be made on the host instead". Currently fails because `git -C sub status` exits 128 with `fatal: not a git repository: sub/../.git/modules/sub` (the dangling gitfile the plan fixes).
- `superproject status and add succeed in the container with an absorbed submodule` — with the gitlink in the container index (populated by the initial `reset --mixed`), asserts `git status --porcelain && git add -A --dry-run` succeed with empty output, and that after modifying `sub/file.txt` inside the container `git status --porcelain` reports ` M sub` (on git 2.47.3 — the version in the image and on the host — porcelain v1 reports submodule modified content as ` M sub`, verified identical with and without the read-only chmod). This pins the plan: "Superproject-level `git status`, `git diff`, `git add -A` and similar index/commit operations inside the container no longer fatal when the project contains a submodule checkout; submodule state is accurately summarized". Currently fails with the same dangling-gitfile fatal, which aborts the whole `git status` rather than degrading (as documented in the linked issue).
- `the container resolves an absorbed module gitdir against the container submodule path` — the submodule is added with `--name module-name` (name ≠ path) and its module `core.worktree` is forced to the absolute host path (`git config --file .git/modules/module-name/config core.worktree "$PROJECT/sub"`) before container creation, reproducing the condition the inclusion-mechanism choice describes ("`git submodule absorbgitdirs` records an **absolute host path** in each module's `core.worktree`, which is invalid inside the container"; verified that a host-side `absorbgitdirs` run during container creation preserves the forced value). Asserts `git -C sub rev-parse --show-toplevel` prints `/working/<project-base>/sub` and `git -C sub status` reports a clean worktree, so the rewrite must resolve the path from `.gitmodules` (`submodule.<name>.path` → `modules/<name>`) rather than copy the host value through. This pins the plan's implementation outline: "Rewrite each copied module's `core.worktree` to a path relative to that module's gitdir (`../../../<submodule-path>`), resolving `<submodule-path>` from the worktree's `.gitmodules`". Currently fails with the dangling-gitfile fatal, and would keep failing if the implementation copied `modules/` without the rewrite (a `core.worktree` pointing at a nonexistent host path inside the container fatals with `Invalid path ... No such file or directory`).
- `the container modules tree is refreshed from the host on every setup run` — a first `onbox -c` run creates the container (fresh-init branch), then a second submodule is added host-side, then a second `onbox -c` run re-runs `setup.sh` against the existing gitdir volume (`run_container` in `lib/containers.sh` runs `run_setup_in_container` on every start, so this exercises the existing-repository branch). Asserts `git -C sub2 status && git -C sub status` succeed. This pins the plan: "The modules tree is refreshed from `/host/git/modules` on every setup run (idempotent replace), so host-side submodule changes propagate into the container gitdir on each container creation/recontain", and also covers the plan's requirement that the inclusion step run "in *both* the fresh-init and existing-repository branches" and cope with the read-only leftovers of the previous copy ("`chmod -R u+w` the stale copy before removal"). Currently fails at the first run's `git -C sub status` fatal; without the refresh the second run's `git -C sub2 status` would fail on the missing `modules/sub2`.

Assertion validation: before writing these tests the container-side layout (worktree + fresh gitdir volume wired as `setup.sh` does, with and without the planned module-inclusion step) was simulated on the host with scratch scripts; every assertion above was observed to fail pre-implementation and pass with the simulated copy/rewrite/chmod mechanism applied, except where noted that only the real container distinguishes the cases (host paths exist during simulation, so the no-rewrite fatality was confirmed via a nonexistent `core.worktree` target).

## Tests edited

- None. No pre-existing test other than the removed one below is affected by the plan: the setup.sh change only activates when `/host/git/modules` exists and is non-empty, and no other e2e or unit test creates submodules, so all other suites remain valid and green (confirmed: unit 307/307 pass, e2e 77/77 of the untouched tests pass).

## Tests removed

- `git operations inside a submodule are blocked within the container` (was in [test/e2e/git-transport.bats](../../../test/e2e/git-transport.bats), superseded by the first new test) — inconsistent with the plan, which explicitly supersedes it: "Supersede the existing 'git operations inside a submodule are blocked within the container' test: it currently asserts `git -C sub status` *fails*, which passes only because the gitdir is missing. It is replaced by assertions that `git -C <sub> status` (read) *succeeds* while a submodule history write (`git -C <sub> update-ref` or an empty commit) *fails* on the non-writable `objects/`/`refs/`." The linked issue's "why tests did not catch it" says the same: "It does fail, but for the wrong reason (the pointed-to git directory is absent) rather than because submodule operations are explicitly prevented." Keeping it would contradict the plan's reimplementation of SPEC.md's prevention clause as targeted write prevention ("reimplemented as targeted write prevention (reads succeed, history writes fail)"), because after implementation `git -C sub status` must succeed and the old assertion would fail.
