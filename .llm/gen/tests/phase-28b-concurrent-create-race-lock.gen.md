# Tests: Phase 28b serialize the create/recreate/rm paths with a per-container lock

Red/green test suite for [the plan](../plans/phase-28b-concurrent-create-race-lock.gen.md), which implements the resolution of [the concurrent-create-rollback-race issue](../issues/concurrent-create-rollback-race.gen.md) by taking an exclusive per-container `flock` around each mutating container-lifecycle critical section (`run_container`'s exists-check/create/start, the whole `run_recreate` plan execution including its rollback failure path, and the whole `run_rm_container`/`run_rm_image` plan executions) so simultaneous invocations serialize and the loser of a create race attaches to the winner's container instead of destroying it, while `fetch`/`merge`/`sync` and the setup/nft/exec tail stay unlocked. No new issue documents were created for this phase.

No core files were edited. Only [test/unit/helpers.bash](../../../test/unit/helpers.bash), [test/unit/containers.bats](../../../test/unit/containers.bats), [test/unit/lifecycle.bats](../../../test/unit/lifecycle.bats), [test/unit/netbox-offbox.bats](../../../test/unit/netbox-offbox.bats), [test/unit/dispatcher.bats](../../../test/unit/dispatcher.bats), [test/e2e/helpers.bash](../../../test/e2e/helpers.bash), [test/e2e/lifecycle.bats](../../../test/e2e/lifecycle.bats) and this document were changed. The plan also lists `lib/locking.sh`, `lib/containers.sh` and `MAP.gen.md` under "Files to be created or modified"; those updates describe the implemented state and are left to the implementation phase.

## Lock helper contract pinned by the unit tests

The plan names the module ("a small new module (e.g. `lib/locking.sh`) — an acquire-and-release around a critical section (fd-based `flock` with the lock held across the section), sourced by `lib/containers.sh`") without fixing the API, so the unit tests pin this contract:

- `lib/locking.sh` sourced via `load_container_libs` (i.e. by `lib/containers.sh`).
- `talkbox_lock_dir` — prints the lock directory: `$TALKBOX_LOCK_DIR` when set (non-empty; the plan's "root overridable for tests" override), else `$XDG_RUNTIME_DIR/talkbox/locks` ("a per-user lock directory such as `${XDG_RUNTIME_DIR}/talkbox/locks`"), else `${TMPDIR:-/tmp}/talkbox-locks-<uid>` ("a per-uid temp fallback").
- `container_lock_path <container-name>` — prints `<lock-dir>/<container-name>`, "keyed by the container name, e.g. `<project-slug>.<container>`".
- `acquire_container_lock <container-name>` — creates the lock directory and file and takes an exclusive, blocking fd-based `flock`.
- `release_container_lock` — releases the lock taken by `acquire_container_lock`.

## New tests

All are new; each fails pre-implementation for a plan-relevant reason and passes once the plan is implemented.

### `test/unit/containers.bats`

- **`the container lock is exclusive and blocks a second acquirer until the holder releases`** — acquires via the helper in a background subshell, proves a second acquirer cannot take the lock (`flock -n` fails) and that a bounded waiter (`flock -w 10`) only succeeds after the holder releases (elapsed ≥ 1s), then proves the lock is free again. Implements the plan's test item "the lock helper acquires exclusively and blocks a second acquirer until release". Fails pre-implementation at `[[ -f "$PROJECT_ROOT/lib/locking.sh" ]]` (the module does not exist yet).
- **`lock files land under the configured per-user lock directory and are named per container`** — pins `container_lock_path`/`acquire_container_lock`/`release_container_lock` against `TALKBOX_LOCK_DIR`, and `talkbox_lock_dir` against the `XDG_RUNTIME_DIR/talkbox/locks` layout, the `${TMPDIR:-/tmp}/talkbox-locks-<uid>` fallback and a set `TMPDIR`. Implements "lock files land under the configured per-user directory and are named per container". Fails pre-implementation: `container_lock_path: command not found`.
- **`the container lock is released when the holding process dies`** — a background holder is killed (children first, since they inherit the lock fd) and the lock must immediately be acquirable again. Implements "The lock file is released on process death (kernel `flock` semantics), so a killed invocation cannot leave a stale lock". Fails pre-implementation: `container_lock_path: command not found`.
- **`run_container holds the container lock across the exists-check, create and start and runs the exec tail unlocked`** — stalls every podman invocation naming the container in the shim and probes, from inside each stalled invocation, whether the container lock is held: the `container exists` probe (the first podman call), the `create` and the `start` must report `held`; the `exec setup.sh`, the user `exec` and the final `stop` must report `free`; after `run_container` returns the lock must be acquirable. Implements the plan's critical-section definition — "from the `container_exists` check through `create_sandbox` and `podman start` (not the setup/nft/exec tail, so concurrent attach sessions proceed in parallel)" — assertable "via the lock file's presence during a shim-stalled create". Fails pre-implementation: no lock is ever taken, so every probe reports `free` and the `held` counts are 0.
- **`a failed create holds the container lock through the rollback of this invocation's resources`** — a netbox create whose plan fails at `podman create` must hold the lock through `rollback_creation_and_die` (the three rollback `volume rm -f` calls each probe `held`), remove exactly the plan's named volumes, keep the `talkbox:` diagnostic, and leave the lock free after the `die`. Implements "`rollback_creation_and_die` is unchanged: under the lock its `podman rm -f`/`podman volume rm -f` can only target resources this invocation's plan created" and the plan's test item "the rollback path under a plan failure removes only this invocation's resources". Fails pre-implementation: the rollback probes report `free`.

### `test/unit/lifecycle.bats`

- **`run_recreate holds the container lock across the whole plan execution`** — the `rm -f --volumes`, `volume rm`, `create` and `start` plan steps of `run_recreate` must each probe `held`. Implements "run_recreate: the whole `plan_recreate` execution including the `podman rm -f --volumes`". Fails pre-implementation: all probes report `free`.
- **`run_recreate holds the container lock through the rollback when the plan fails`** — a recreate whose plan fails at `podman start` must hold the lock through the rollback's `podman rm -f` (the plan's own `rm -f --volumes` line is deliberately not matched by the stall pattern) and still remove the gitdir volume, keeping the `talkbox:` diagnostic. Implements the plan's "including ... its `rollback_creation_and_die` failure path". Fails pre-implementation: the rollback probe reports `free`.
- **`run_rm_container holds the container lock across the plan execution`** — the `rm -f --volumes`, a `volume rm` and the `rmi` root-image steps must each probe `held`. Implements "run_rm_container ... the whole plan execution". Fails pre-implementation: all probes report `free`.
- **`run_rm_image holds the container lock across the plan execution`** — the `rmi <base-image>` step must probe `held`. Implements "run_rm_image ... the whole plan execution". Fails pre-implementation: the probe reports `free`.

### `test/e2e/lifecycle.bats`

- **`onbox concurrent first invocations: both succeed and attach to the one created container`** — two simultaneous first invocations on a fresh project (launched back-to-back, each in its own held-open `sdrun` unit — see the note below) must both exit 0, exactly one `podman create` must appear in the shared logging shim's log, no destructive `rm -f <ctr>` (rollback) line may appear, and the container must exist and remain usable (`-c --noninteractive` write+read probe) afterwards. Implements the plan's external-facing item "Two or more simultaneous first invocations of the same container command ... exactly one creates the container; the loser of the race waits for the lock and then sees the winner's container as existing and attaches to it. No `cannot create container` rollback firing on another invocation's container." Fails pre-implementation: without the lock both invocations race on `podman create`, the loser's rollback destroys the winner's container, and one session exits non-zero.
- **`onbox concurrent rm-container serializes behind the create instead of interleaving with it`** — a first invocation whose `podman create` is stalled for 4s inside a delegating shim, with `onbox --rm-container` launched 0.5s into the race: the removal invocation must exit 0, and its `rm -f --volumes` line must be timestamped *after* the creating invocation's `start` line (the lock covers the create critical section through `podman start`), after which the container is gone. Implements the plan's external-facing items "`--recontain`/`--rebuild` and `--rm-container`/`--rm-image` are mutually exclusive with a concurrent create or attach session of the same container" and "a concurrent `--rm-container` does not interleave with a create in a way that removes the freshly created container". Fails pre-implementation: `podman rm -f` is a no-op on a not-yet-created container, so the removal completes *before* the create critical section (timestamp ordering fails).

Two deviations from the plan's literal e2e wording, for test-engineering reasons only:

- The plan's example is "`onbox -c --noninteractive 'true'` launched concurrently"; the first-invocation test uses `'sleep 2'` for both invocations so each session is still live when the other's exec-session listing is taken, keeping the milliseconds stop-decision race window (acknowledged by the phase-28a choice) out of the asserted path — the same reason the phase-28a e2e tests use `sleep` sessions. The serialization behaviour asserted is identical.
- Both concurrent invocations are launched through `run_onbox_session_holding_unit` (held open for 10s past the session), because a session's unit deactivation (`KillMode=control-group`) destroys the container started inside that unit — the same mechanism the phase-28a tests hold open. Without the holds, the winning unit's deactivation would kill the container under the loser's live session even with the lock in place.
- The first-invocation test uses a non-git project (`rm -rf "$PROJECT/.git"`) so the two concurrent `setup.sh` runs cannot contend on git ref/config locks (a spec-mandated per-invocation step, hazard documented in the multi-terminal review); the create-race behaviour under test is git-independent.

## Edited tests

No pre-existing *test case* was changed; the edits are confined to test harness plumbing, required by the plan's test items, and every pre-existing test still passes in the red run (314 unit, 83 e2e):

- [test/unit/helpers.bash](../../../test/unit/helpers.bash) — `make_podman_shim` gains the env-driven stall feature (`PODMAN_STALL_PATTERN`/`PODMAN_STALL_SECONDS`/`PODMAN_STALL_HOOK`), placed after the invocation log and before the failure handling, so a test can observe external state (the lock) from inside a stalled podman invocation, per the plan's "assertable via the lock file's presence during a shim-stalled create". The shim itself stays flock-oblivious per the plan's "the podman shim is oblivious to flock" — the flock probing lives in the caller-provided hook. New helpers: `grep_count`, `make_lock_probe_hook` (records `held|free <invocation>` per stalled invocation; a missing lock file means no lock was ever taken and reports `free`) and `lock_is_free` (a missing lock file counts as released, an existing one must be acquirable non-blockingly).
- `setup()` in [test/unit/containers.bats](../../../test/unit/containers.bats), [test/unit/lifecycle.bats](../../../test/unit/lifecycle.bats), [test/unit/netbox-offbox.bats](../../../test/unit/netbox-offbox.bats) and [test/unit/dispatcher.bats](../../../test/unit/dispatcher.bats) — exports `TALKBOX_LOCK_DIR="$BATS_TEST_TMPDIR/locks"`, the plan's "root overridable for tests" knob, so the four files that drive the mutating cores write their lock files into the per-test tempdir instead of the user's real runtime-dir lock directory, keeping the suite hermetic the way `mk_talkbox` neutralises default mounts for e2e.
- [test/e2e/helpers.bash](../../../test/e2e/helpers.bash) — `sdrun` forwards `TALKBOX_LOCK_DIR=$E2E_LOCK_DIR` into every unit when `e2e_setup` has set one (per-test lock directory, so e2e lock files stay out of the user's runtime dir); `run_onbox_session_holding_unit` now prepends the registered podman shim directory to PATH exactly like `run_talkbox`, so held-open concurrent sessions can log their podman calls for the create-count/no-rollback assertions; new `mk_podman_stalling_shim` logs every invocation as `<epoch-millis>\t<args>` and delegates to the real podman, sleeping first for a named subcommand, which is what lets a test launch a second invocation into an open create critical section and order one invocation's step against another's.
