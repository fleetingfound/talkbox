# Choice: `merge` / `sync` failure behaviour on `--all`

Related review: [git-transport-review](../reviews/git-transport-review.gen.md) (observation 2)

## Context

`run_merge` in [lib/git.sh](../../lib/git.sh) processes branches with `custom_merge "$container" "$b" || rc=1`, continuing to the next branch after a failure and returning a non-zero exit at the end. The `sync` script (generated by `sync_script`) uses `custom_merge host "$b" || exit 1`, stopping immediately on the first failure.

With `--all`, this means `merge --all` processes every branch and reports overall failure, while `sync --all` stops at the first non-descendant or dirty-worktree branch and skips the rest. [SPEC.md](../../SPEC.md) does not prescribe either behaviour, so neither is a spec violation, but the asymmetry could surprise users expecting consistent `--all` semantics.

## Options

### Option A — Make `sync` continue on failure like `merge` (Recommended)

Change the sync script's per-branch loop from `custom_merge host "$b" || exit 1` to `custom_merge host "$b" || rc=1`, processing all branches and exiting non-zero if any failed. This matches `run_merge`'s existing behaviour.

**Pros:** consistent `--all` semantics across `merge` and `sync`; the user sees all failures in one pass rather than having to re-run after each fix; smaller change (align `sync` to `merge`).
**Cons:** a dirty worktree or non-descendant on one branch no longer blocks subsequent branches — but since each `custom_merge` is independent and fast-forward only, processing subsequent branches is safe.

### Option B — Make `merge` stop on failure like `sync`

Change `run_merge`'s per-branch loop from `custom_merge "$container" "$b" || rc=1` to `custom_merge "$container" "$b" || exit 1`, stopping at the first failure.

**Pros:** consistent `--all` semantics; avoids processing further branches after a failure that might indicate a broader issue.
**Cons:** the user only sees the first failure and must re-run after each fix; regresses the existing `merge` behaviour; a non-descendant on one branch would block unrelated branches.

### Option C — Keep the current asymmetry

No change. `merge` continues on failure, `sync` stops on first failure.

**Pros:** no change required; no risk of regression.
**Cons:** the asymmetry remains and could surprise users.

## Recommendation

**Option A.** Processing all branches in one pass is more useful (the user sees all failures), each `custom_merge` is independent and safe to run in sequence, and aligning `sync` to `merge`'s existing behaviour is the smaller, lower-risk change.

## Selected option

**Option B (selected by the user).** Change `run_merge`'s per-branch loop from `custom_merge "$container" "$b" || rc=1` to stop on the first failure, matching `sync`'s existing `|| exit 1` behaviour. Both `merge --all` and `sync --all` now stop at the first non-descendant or dirty-worktree branch.
