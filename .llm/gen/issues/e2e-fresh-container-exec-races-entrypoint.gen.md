# Issue: e2e commands executed on a freshly started container race the entrypoint

The `run_onbox`/`run_netbox`/`run_offbox` executors in [lib/containers.sh](../../../lib/containers.sh) run `podman exec` immediately after `podman start`, without waiting for [image/entrypoint.sh](../../../image/entrypoint.sh) to finish its start-up work (dotfiles copy, git identity config writes, and the gitdir-volume `git init`/`git fetch host`/`git reset --mixed` block). Under load — repeated back-to-back suite runs, accumulated leftover containers and named volumes from test teardowns (e.g. `test/e2e/onbox.bats` leaks `<slug>.onbox.gitdir` named volumes) — an exec'd command can run before the entrypoint completes, so git commands in a fresh container intermittently fail (`git log` before the initial reset, `git commit` before the repo is initialised, `git config user.name` before the global config is written, or `netbox --rm-image` tripping the `image_in_use` guard when a leftover container still references the base image).

The full e2e suite passes 67/67 in a clean environment but fails intermittently on a state-polluted one, hitting different git-touching tests on different runs (git-identity, git-transport, lifecycle recontain, netbox --rm-image). The entrypoint's pre-init identity writes added by Phase 9b lengthen the pre-init window, slightly widening this race. A proper fix would make the executors wait for entrypoint readiness before exec, and make test teardowns remove named volumes and tolerate partial container sets.
